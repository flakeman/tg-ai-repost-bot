# ADR-012: Укрепление параллелизма SQLite и обязательный busy_timeout на каждом соединении

## Статус
Принято (Accepted)

## Контекст
1. SQLite используется в режиме WAL (`Write-Ahead Logging`), что обеспечивает одновременное чтение несколькими потоками и асинхронную запись.
2. В SQLite директива `PRAGMA busy_timeout = 5000` задаёт время ожидания освобождения файла базы данных при конкурентной блокировке. Однако директива действует только на то соединение, в котором она была выполнена.
3. В исходной реализации `SqliteJobRepository` на каждый запрос открывал новое соединение `aiosqlite.connect(self.db_path)`, но не выставлял `busy_timeout`. При одновременном выполнении фонового воркера и обработчика команды возникал риск ошибки `sqlite3.OperationalError: database is locked`.

## Решение
1. **Фабрика соединений:**
   Создать централизованную фабрику/контекстный менеджер соединений `get_db_connection(db_path: str)`, которая гарантированно выполняет при открытии каждого соединения:
   ```python
   async with aiosqlite.connect(db_path) as db:
       await db.execute("PRAGMA busy_timeout = 5000;")
       await db.execute("PRAGMA journal_mode = WAL;")
       db.row_factory = aiosqlite.Row
       yield db
   ```
2. Использовать фабрику во всех методах `SqliteJobRepository` и `SqliteSettingsRepository`.

## Последствия
- Положительные:
  - Исключение ошибок `database is locked` при одновременной записи нескольких задач.
  - Потокобезопасная и асинхронно-безопасная работа SQLite без перехода на тяжелые внешние СУБД (Postgres).
- Ограничения:
  - Небольшая микрозадержка (до нескольких миллисекунд) при наличии параллельной блокировки, что полностью покрывается временем ожидания.
