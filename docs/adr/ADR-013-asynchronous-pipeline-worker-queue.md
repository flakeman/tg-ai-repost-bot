# ADR-013: Асинхронная очередь задач обработки (In-Memory Worker Queue)

## Статус
Принято (Accepted)

## Контекст
1. Пайплайн обработки публикации состоит из ресурсоёмких шагов:
   - Загрузка и парсинг веб-страницы (1–5 сек)
   - Рерайт текста в LLM (5–20 сек)
   - Генерация изображения через DALL-E / cheapvibecode (10–30 сек)
2. Ранее весь этот конвейер выполнялся прямо внутри Telegram-хэндлера `handle_incoming_content`. В течение 30–60 секунд обработчик удерживал соединение бота.
3. Это приводило к следующим проблемам:
   - При отправке нескольких ссылок подряд бот не отвечал на другие команды.
   - При сетевом сбое между Telegram и ботом обработка прерывалась.
   - Пользователь не видел четкого прогресса в очереди.

## Решение
1. **Декуплинг (разделение) приёма и обработки:**
   - Хэндлер `handle_incoming_content` регистрирует задачу в БД со статусом `PENDING`, отправляет пользователю карточку «⏳ Задача добавлена в очередь обработки» и немедленно освобождает Telegram event loop.
   - Задача помещается в асинхронную очередь `asyncio.Queue`.
2. **Фоновый воркер `PipelineQueueWorker`:**
   - Фоновая задача `asyncio.create_task(worker.start())` непрерывно забирает задачи из очереди.
   - Выполняет конвейер `process_pipeline(job_id)`.
   - По завершении редактирует статусное сообщение или отправляет готовое интерактивное превью автору в личные сообщения.
   - Поддерживает контролируемый уровень конкурентности (concurrency limit = 1..2), предотвращая перегрузку CPU и памяти на сервере.

## Последствия
- Положительные:
  - Мгновенный отклик бота на любые сообщения пользователей (< 200 мс).
  - Защита от зависания long-polling Telegram.
  - Упорядоченная обработка постов без взаимных коллизий.
- Ограничения:
  - При перезапуске процесса PM2 незавершённые задачи из очереди в оперативной памяти подхватываются механизмом Startup Recovery (ADR-014).
